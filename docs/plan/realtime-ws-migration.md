## 2. 실측 결과 (2026-07-31, 실계좌 읽기 전용 구독)

### 2.1 프로토콜·연결 — 전부 확인
| 항목 | 결과 |
|---|---|
| WS 접속 | ✅ |
| 공유 kiwoom 토큰으로 LOGIN | ✅ `return_code:0` (REST 주문 세션과 병행 무충돌) |
| `0B` 등록 (KRX + `_NX` 동시) | ✅ `return_code:0` |
| `00` 주문체결통보 등록 | ✅ `return_code:0` (별도 `grp_no` 로 동시 등록) |
| KRX 실시간 틱 | ✅ 15:30:18 종가 단일가 체결 수신 |
| **NXT `_NX` 실시간 틱** | ✅ **005930 9,602틱/300초(32틱/초) · 000660 4,351틱** |
| 틱 신선도 | 0.4~1.0초 |
| 틱 필드 | `10` 현재가(±부호) · `20` 체결시각 · `9081` **거래소 구분(KRX/NXT)** · `15` 체결량 |

`9081` 이 있어 심볼 문자열이 아니라 서버 값으로 보드를 구분한다 — 캐시에서 보드를 오인할 여지가 없다.

### 2.2 ⚠️ 초안의 전제 하나가 반증됨
"NXT 현재가를 일봉 근사로 얻으므로 부정확하다"를 검증했더니 **세션 중에는 정확했다.**
WS 실시간가 vs 현행 `get_market_price` 를 15초 간격 40회 비교:

| | 결과 |
|---|---|
| 차이 0원 | 32/40 (80%) |
| 차이 있음 | 8/40, 전부 500~2,000원 = **0.06~0.20%** |

`kiwoom_data_client.py` 주석의 *"NXT 거래시간 중엔 당일 캔들이 실시간 갱신된다"* 가 맞았다.
남은 0.2%도 REST 왕복 0.35초에 낀 1~2틱 시차로 설명된다.

### 2.3 대신 발견한 것 — 세션 공백 구간 (미해결)
```
15:36  get_market_price = 265,000  ← NXT 15:20 마감가에 고정(16분 전)
       같은 시각 KRX 종가 262,500    → 괴리 +0.95%
15:42  get_market_price = 254,000  ← 애프터마켓 열리자 갱신
```
일봉 근사는 **세션 중엔 정확하고 세션 공백에서만 어긋난다.** monitor 가동 구간에도 공백이 있다 —
NXT 프리마켓 종료(08:50 추정)~KRX 개장(09:00) 약 10분. 이 구간엔 하드손절이 최대 10분 묵은
가격으로 판정될 수 있다. **WS 도 이 구간엔 체결이 없어 틱이 없으므로 이번 변경으로 해결되지 않는다.**
→ 별건. 08:40~09:05 관측으로 프리마켓 마감 시각과 캔들 정지를 확인한 뒤,
   공백 구간엔 KRX `cur_prc` 로 폴백하는 처리를 검토한다(WS 무관, `kiwoom_data_client` 국소 변경).

### 2.4 비용 실측
`get_market_price` 1회 = REST 2콜(ka10100+ka10081), 왕복 ≈0.4초. 보유 10종목이면 15초마다
20콜·약 4초를 가격 조회에만 쓴다. 구독 후에는 0콜.

## 3. 최종 설계 (구현된 것)

### 3.1 원칙
- **WS 는 항상 옵셔널.** 연결 실패·무틱·TTL 초과 → 기존 REST 경로로 폴백. WS 가 죽으면 종전 동작과 동일.
- **민감 파일 무변경**: `execution_engine.py`, `risk_engine.py` 손대지 않음.
- **금액 집계는 ka10076 유지.** 통보는 "지금 동기화해라" 트리거로만 쓴다 — 실시간 통보를 단일
  소스로 삼으면 한 건 유실에 포지션이 조용히 틀어진다(`reconcile` 이 존재하는 이유와 같은 원칙).
- **자금 경로 회귀 금지**: `check_once` 는 시그니처·거동을 그대로 보존(기존 테스트 123개 무수정 통과).

### 3.2 판정 주기를 하나가 아니라 셋으로 분리 — 핵심 결정
`POLL_SEC=1` 로 일괄 변경하면 판정만 빨라지지 않고 **주문 전송과 DB 쓰기까지 초당 1회**가 된다.

| 동작 | 주기 | 근거 |
|---|---|---|
| 뉴스베토·하드손절·스탑 breach **판정** | **틱 즉시**(무틱 시 1초 백스톱) | 15초 폴링은 노이즈 필터가 아니라 **무작위 샘플링**이다. 진짜 하락이면 손절선보다 낮게 팔리고(확실한 손실), 순간 급락이면 운에 맡긴다. 2026-07-18 백테스트에서 '확인틱'(지연 추가)이 현행보다 나빴던 것과 같은 방향이고, 그 백테스트는 1분봉이라 15초/1초를 구분할 수 없었다 |
| 매도 주문 **전송·재시도** | 종목별 **15초 쿨다운** | 2026-07-10 HLB 하한가 때 15초 주기로도 거부 238건. 초당 재시도면 시간당 수천 건 → 키움 유량 제한에 걸려 **정작 하한가 풀림을 놓친다**. 재시도 자체는 유지(백오프 기각 결정 불변) |
| 트레일링 스탑 **상향** | 15초(기존) | TRAIL_PCT=0.75 가 15초 주기 백테스트로 튜닝된 값. 상향을 촘촘히 하면 실효 TRAIL_PCT 가 좁아져(비채택된 0.5 쪽으로) 파라미터가 무단 변경된다. breach 감지는 즉시라 스탑선은 그대로 두고 청산가만 선에 붙는다(순 개선) |
| 유지보수(체결동기화·미체결정리) | 15초 + **통보 시 즉시** | 지연 무해 |
| 개장 워밍업(08:00·09:00 1분) | 유지 | 얇은 호가 단발 체결로 칼손절이 오발동하는 위험은 가격 출처가 REST 든 WS 든 같다 |

### 3.4 사후 채점 (비용 0)
손절/스탑/베토 audit payload 에 `path`(tick|slow)와 `slow_wait_ms`(15초 폴링이었다면 더

> ⚠️ **첫 live 는 실계좌·실포지션이다.** `TRADING_MODE=live` 이고 2026-07-31 기준 보유 7종목
> (000270·010120·012330·035420·042660·058610·064350)이 있다. 즉 08-03 08:00 monitor 는
> 실제 손절 권한을 가진 채 새 코드로 돈다. 장 마감 후 구현이라 **실 틱 경로를 사전 검증할 창이 없었다.**

> (동시 WS 세션이 거부되지 않음은 확인됨).

## 4-1. 후속: 대시보드도 같은 WS 로 (2026-08-04)

모니터 탭이 15초 폴링으로 보던 현재가를 **같은 키움 WS 틱**으로 바꿨다(`core/price_stream.py` +
`GET /monitor/stream` SSE + 프론트 `useLivePrices`). 워커 피드는 워커 프로세스 안에 있어 API 가
볼 수 없으므로, API 가 **자기 세션을 따로 붙인다** — 대신 §2.1 의 미검증 항목(같은 토큰 동시 세션의
틱 동시 수신)을 감안해 **모니터 탭 구독자가 있는 동안만** 살리고 30초 유예 후 닫는다. 겹치는 시간이
'사람이 보는 동안'으로 한정되고, 그때 워커 하트비트 `ws.ticks`/`reconnects` 로 간섭 여부를 바로 볼 수
있다(이상하면 `PRICE_STREAM_ENABLED=0`). 표시 전용이라 주문·판정은 경유하지 않고, REST 콜은 오히려
줄어든다(폴링이 종목당 2콜씩 쓰던 것을 스냅샷 재사용으로 대체).

- ✅ 확인(2026-08-04 20:58, 장 마감 후): 401 게이트 · WS LOGIN·13심볼(7종목 양 보드) REG 수락 ·
  SSE 1초 프레임 · 구독 해제 30초 후 세션 종료 · 무틱 구간 REST 폴백(`src:"rest"`)이 `/monitor` 와 동일값
- ⏳ 미검증: **틱이 흐르는 시간대의 live 표시**(8/5 08:00~09:30 또는 NXT 세션) + 그때 워커 피드와의 동시 수신
