# 종가베팅 개편 계획 — "예측 공장"에서 "실험 공장"으로

> 작성: 2026-07-04. 이 디렉터리는 종가베팅 파이프라인 개편의 **전체 설계·단계별 실행 계획**이다.
> 각 단계의 세부 구현은 번호 문서(01~06)에 있고, 이 README 는 전체 그림과 원칙을 설명한다.

---

## 1. 왜 바꾸는가 — 문제의 재정의

현재 파이프라인의 암묵적 전제는 **"내일 갭상승할 종목을 오늘 더 잘 맞히면 수익이 늘어난다"**이다.
그런데 실측 데이터가 이 전제를 반박했다:

- **종합점수와 익일 손익이 역상관** (2026-07-03 승률 분석). 점수를 잘 만드는 방향의 개선이 헛돎.
- 그럴듯했던 팩터가 실제로는 역효과: 대장주 가점(승률 -3%p), 프로그램 양매수(갭 승률 9.1%, n=33).
  → **"그럴듯함"과 "엣지"는 다르다**는 것이 이 프로젝트가 돈으로 배운 교훈.
- 청산 시각 3분 차이(08:03 vs 08:05)가 평균 +0.35% — **팩터 하나보다 큰 엣지가 청산 타이밍에 있었다**.

제1원칙으로 환원하면 종가베팅의 본질은 예측이 아니라:

> **오버나잇 수익률 분포에서, 조건부 기대값이 거래비용보다 크게 양(+)인 부분집합을 찾아,
> 꼬리 리스크를 자르며 반복 추출하는 통계 사업.**

물리적으로 못 뚫는 제약은 4개뿐이다. 나머지는 전부 바꿀 수 있는 관성이다.

| 물리 제약 | 함의 |
|---|---|
| ① 내일 시가를 결정하는 정보(오늘 밤 미국장·새벽 뉴스)는 오늘 15:30에 존재하지 않음 | 개별 예측 정확도엔 천장이 있다. 가능한 건 **조건부 기저율** 측정뿐 |
| ② 갭업 노출과 갭다운 노출은 분리 불가(손절은 개장 전 작동 안 함) | 리스크는 제거가 아니라 분산·사이징·조건부 진입으로 **조절**만 가능 |
| ③ 거래비용 하한(세금+수수료+슬리피지) | 비용 미차감 기대값은 전부 허수 |
| ④ 하루 1 거래일 표본 — 캘린더 시간은 압축 불가 | 유일한 우회로: **유니버스 단면 × 결과 라벨 다중화**로 표본 폭 확장 |

따라서 개편의 방향은 "더 잘 맞히는 시스템"이 아니라
**"무엇이 실제로 돈이 되는지 매일 자동으로 배우는 시스템"**이다.
예측 정확도에는 물리 한계가 있지만, 학습 속도에는 없다.

## 2. 핵심 설계 — 두 축의 결합

### 축 1: 인과 기반 가설 생성 (무엇을 검증할 것인가)

갭상승은 "내일 아침 누군가 더 비싸게 사야만 하는 상황"에서 나온다. 매수자 유형별로
가설 계열(rule family)을 나눈다 — 상관관계 조합이 아니라 **인과 메커니즘**에서 출발해야
과적합에 강하고, 죽었을 때 왜 죽었는지 설명이 된다.

| Family | 매수자 | 가설 골자 | 데이터 |
|---|---|---|---|
| **F3 NXT 괴리형** | 본장 유동성 재진입자 | 애프터마켓 괴리(질이 좋은)는 본장에서 재정렬된다 | ✅ 전부 사내(kiwoom NXT) |
| **F1 뉴스 미반영형** | 장 마감 후 해석 매수자 | 신규 재료 대비 가격 반응이 부족한 종목이 아침에 재가격화된다 | ✅ 뉴스 라벨 6컬럼 기구축 |
| **F2 해외 동조 지연형** | 섹터 리밸런싱 매수자 | 밤사이 해외 참조가격 변화를 국내 관련주가 아침에 따라간다 | ✅ yfinance+KIS 기구축 |
| **F4 후발 확산형** | 대장주 놓친 추격 매수자 | 대장주 급등 후 동섹터 저반응 후발주로 관심이 이동한다 | ✅ 주도주·섹터 기구축 |
| **control** | (대조군) | 현행 종합점수 top-10 — 새 가설이 이겨야 할 기준선 | ✅ 현행 그대로 |
| **veto** | (감액 전용) | 나쁜 매매 제거(악재 뉴스·유동성 함정 등). 수익 가설이 아니라 꼬리 절단 | 일부 기구축 |

### 축 2: Edge Ledger — 검증 원장 (어떻게 승격시킬 것인가)

**모든 가설은 candidate 로 태어나 페이퍼 성적으로만 승격된다. 표본 없이 돈을 만지는 가설은 없다.**

```
[가설 등록]  edge_rule 테이블 — 반증가능한 조건(JSON predicate) + 인과 근거 필수
     │  status: candidate ──(표본·성적 충족 + 수동 승인)──► live ──(성적 붕괴)──► retired
[매일 평가]  rule_evaluator 워커(09:40) — 전 유니버스에 predicate 적용 → 결과 라벨 조인
     │       → 비용 차감 기대값·승률·신뢰구간 자동 갱신 → 승격/강등 후보 텔레그램 알림
[집행]      live rule 매칭 종목만 trade_signal 핸드오프 (rule_id 태깅 → 손익 귀속 관통)
```

기존 흐름과의 차이를 한 줄로:

```
기존:  콘텐츠 → 종합점수 → top-10 → 매수 → 청산 → (주간 가중치 미세조정)
개편:  유니버스 전체 기록 → 모든 가설 페이퍼 평가 → 검증된 가설만 집행 → 결과가 가설로 자동 귀속
```

### 일정 감각 (표본 축적이 임계 경로)

```
7/6 주     Phase 1+2 구현·배포 ──────────► 표본 축적 시작 (이게 임계 경로)

7월 말     뉴스 라벨 검증(기존 일정과 정합) + rule 중간 성적 점검

```

유니버스 일 40~70종목 기준 rule 당 매칭 3~10종목/일 → **n=40 도달에 약 4~8주**.
구현을 아무리 빨리 해도 이 시간은 못 줄인다(물리 제약 ④). 그래서 Phase 1·2 가 최우선이다.

## 5. 운영 원칙 (전 단계 공통 — 이것이 규율이다)

1. **사전 등록 원칙 (pre-registration)**: rule 은 등록 시점 이후의 out-of-sample 표본으로만
   승격을 판정한다. 과거 데이터를 뒤져 만든 rule 의 과거 성적은 참고용일 뿐 승격 근거가 아니다.
   (데이터 스누핑 → 과적합 차단. 다중 가설을 동시 검증하므로 특히 중요.)
2. **비용 차감 원칙**: 모든 기대값은 `EDGE_COST_PCT`(왕복 비용, 기본 0.25%) 차감 후 값으로만
   비교한다. 상수는 trading `fill` 의 실측 수수료·세금으로 주기 보정한다.
3. **인과 근거 필수**: rule 등록 시 "누가 왜 내일 아침 사는가"를 description 에 명시한다.
   설명 못 하는 상관관계 조합은 등록 금지.
4. **reduce-only 예외**: veto(감액·제외 전용) rule 은 기대값 검증 없이 조기 적용 가능 —
   수익 가설이 아니라 측정 불가능한 꼬리를 자르는 물리 제약 대응이기 때문. 단 적용 내역은 기록.
5. **무거래가 기본값**: live rule 이 매칭 0 이면 그날은 사지 않는다(Phase 4 이후).
   거래 안 함도 포지션이다.
6. **대조군 상시 유지**: `control_legacy_top10`(현행 점수 방식)은 페이퍼로 계속 평가한다.
   새 가설은 절대 기준(비용 초과 수익)과 상대 기준(대조군 우위)을 모두 이겨야 한다.

## 6. 가드레일 (건드리지 않는 것)

- `jongalab/core/trading_engine.py` · `prompts.py` — **수정하지 않는다.** 점수 계산은 현행 유지
  (대조군으로 계속 필요). 선정 전환은 `closing_bet.py`(비가드) 레벨에서 selected 판정만 바꾼다.
- `trading/core/risk_engine.py` · `execution_engine.py` — **수정하지 않는다.** 킬스위치·서킷브레이커·
  멱등키·시드 배분·청산 흐름 전부 무변경. trade_signal 계약에 nullable 컬럼 1개만 추가(하위호환).
- 기존 매매 행위는 Phase 4 승인 전까지 **완전 불변**. Phase 1~3 은 순수 관측·기록 레이어다.
- DB 접근은 `core/repository/*`, LLM 은 `ai_service.analyze_content` 경유 — 기존 아키텍처 규칙 그대로.

## 7. 명시적 비범위 (지금 안 하는 것)

- 진입 시간대 다변화(15:40~16:30, 18:00~20:00 진입) — 표본만 분산시킴. 시간대는 추후 rule 속성으로.
- 틱 데이터 기반 체결 연속성 지표 — 인프라 비용 대비 후순위. 애프터 거래대금으로 근사.
- 검색량·커뮤니티 크롤링 (F5 관심 확산형) — 데이터 취득 비용 큼. 보류.
- Exit Router 자동화(rule 별 청산창 자동 선택) — 다중 청산 라벨이 쌓인 뒤의 일. 지금은 라벨만 수집.
- weight_tuner 폐기 — 하지 않는다. 대조군 유지 장치로 존치하고, 추후 "rule 제안자"로 역할 전환.

## 8. 단계 공통 검증 절차

각 Phase 문서에 개별 검증이 있고, 공통으로:

1. Python 변경 → `uv run --directory jongalab python -m py_compile <file>`
2. 순수 로직(predicate 평가기 등) → `tests/` 추가 후 `uv run --directory jongalab --group dev pytest`
3. 라우터 → API 기동 후 `curl` 로 status·shape 확인
4. 워커 → 단발 실행(`uv run --directory jongalab workers/<name>.py`)으로 로그·DB 반영 확인
5. 프론트 → `npx tsc --noEmit && npm run lint` + **모바일 레이아웃 우선** 확인
6. 스키마 → `sql/2. create_table.sql`(정본) 갱신 + 번호 붙은 마이그레이션 파일 추가 (기존 관례)
7. 주요 로직 변경 시 해당 도메인 `README.md` 동기화 (AGENTS.md 규칙)
