## 2. 진단

세 가지를 차례로 확인해 배제했다.

1. **CTR 0.5%는 이상치가 아니다.** 게재순위 19.7위의 기대 CTR이 0.5~1%다. 스니펫 문제가 아니다.
2. **얇은 페이지가 노출을 잠식한 것도 아니다.** `/stocks/` 2,921개가 만든 노출은 157회로,
   페이지당 0.05회다. CTR을 끌어내린 게 아니라 **애초에 색인되지 않았다**.
3. **실제 원인은 의도 불일치다.** 리포트 상세는 평균 7위라 순위는 이미 확보돼 있는데 클릭이 0이다.
   노출을 만든 검색어가 전부 "종목명 + 날짜 + 종가" 형태 — **시세 조회 의도**인데,
   종가랩 페이지는 추천 근거를 담고 있어 답이 되지 않는다. 게다가 그 질문은 구글 금융 카드와
   네이버금융이 SERP 상단에서 즉답하므로 7위까지 내려올 이유가 없다.

왜 그 검색어에만 걸렸는지는 메타태그가 그대로 설명한다. 당시 리포트 상세는
제목이 `{종목명} · {날짜} 리포트`, description이 `수급 A(8.5점) | 종합 85점 | 기관 +120억 |
외인 +80억` 이었다. 제목의 **종목명 + 날짜**, description의 **외인/기관 순매수**가
"삼성전자 8월 11일 2026 종가 외국인 순매수" 같은 쿼리와 정확히 맞물렸다.

**결론: 기술적 SEO 문제가 아니라 검색 수요와 콘텐츠가 만나지 않는 문제다.**
사이트는 종목 데이터를 나열하는데, 종목 데이터 쿼리는 네이버금융이 전부 가져간다.
종가랩이 이길 수 없는 싸움에 서 있다.

## 3. 이미 적용한 조치 (2026-08-14)

손실을 멈추는 작업만 먼저 반영했다. 트래픽을 늘리는 조치는 아니다.

- **`/stocks/` 색인 대상 축소** — `app/sitemap.ts`가 티커 사전 전체(2,921개) 대신
  **리포트 이력이 있는 종목만** 싣는다. 콘텐츠도 리포트도 없는 종목 페이지는
  `generateMetadata`가 `robots: { index: false }`를 준다.
- **리포트 제목·description 재작성** — 날짜를 제목 앞에서 괄호 뒤로 밀고 앞머리에 검색 의도
  키워드("종가베팅 추천", "추천 근거")를 뒀다. description에서 순매수 금액 나열을 걷어내고
  "왜 골랐나"로 바꿨다. 시세 조회 쿼리 매칭을 줄이려는 것이다.
- **당일 리포트 상세를 사이트맵에 포함** — 이전에는 `/reports/{당일}/{종목}` 10개가 사이트맵에
  없었다(갭 미확정 데이터의 캐시 오염을 피하려 당일을 통째로 제외). 종가베팅은 당일 장 마감
  전에 사는 전략이라 **그 페이지는 하루 지나면 검색 가치가 대부분 사라진다.** 당일치만
  `cache: "no-store"` 로 읽어 원래 가드의 의도(Data Cache 오염 방지)를 지키면서 URL은 싣는다.
  당일치 `changeFrequency` 는 `daily` 로 둬 다음날 아침 갭 결과가 채워진 뒤 재크롤될 여지를 남긴다.

## 3-2. 타겟 쿼리 착수 (2026-08-18)

아래 4번의 결정을 내리고 1차분을 반영했다.

- **타겟 쿼리는 `종가베팅 승률` · `종가베팅 수익률` 2개로 좁힌다.** `AI 주식 추천 수익률` 계열은
  경쟁이 더 두꺼워 같은 노력으로 잡을 확률이 낮다. 성적 서술은 **자동 생성**으로 간다
  (수기 작성은 매 거래일 갱신을 감당할 수 없다).
- **`/record` 에 서술형 본문 추가** — `lib/record.ts` 가 `RecordSummary` 값만으로 문장을 만들고
  `components/pick/RecordNarrative` 가 요약 패널 아래에 렌더한다(h2 "종가베팅 승률과 수익률").
  같은 빌더로 메타 description 도 동적으로 만든다(정적 문구 → 실제 승률·평균 수익률).
  숫자·차트뿐이라 검색엔진이 읽을 본문이 없던 문제(4절 '현재 격차')를 푸는 조치다.
- **`/lab/[name]` 개별 URL 색인 시작** — 사이트맵이 **검증 거래일 10일(`PROMO_MIN_DAYS`) 이상**
  쌓인 룰만 싣는다(2026-08-18 기준 52개 중 32개). 표본이 몇 줄뿐인 룰을 실으면 3절에서
  걷어낸 얇은 페이지를 다시 만드는 셈이라 문턱을 뒀다.
- **`/lab`·`/lab/[name]` description 신설** — 상세는 역할(매수/위험 회피/측정용)을 앞에 붙이고
  성적을 룰 설명보다 먼저 쓴다. 역할을 빼면 제외 규칙 성적이 매수 수익률처럼 읽히고,
  성적을 뒤로 밀면 스니펫에서 잘린다.

**월별 페이지(`/record/{YYYY-MM}`)는 만들지 않는다.** 보류가 아니라 현 시점 판단은 '불필요'다.
1. 같은 달력이 이미 `/record?month=YYYY-MM` 으로 있고 달력 네비게이션 링크로 크롤된다.
   canonical 을 `/record` 하나로 모아 신호를 합쳐 둔 상태인데, 경로를 따로 파면 같은 콘텐츠가
   두 URL 로 갈린다.
2. 월별 승률·평균 수익률 문장을 쓸 수단이 없다 — `record-summary` 는 `days` 기반이라 월 구간
   집계 API 가 없다. 지금 파면 **본문 없이 달력만 있는 페이지**가 되는데, 그게 3절에서 걷어낸
   얇은 페이지와 같은 형태다.
3. 타겟 쿼리와 무관하다. `종가베팅 승률` 의 답은 누적 성적이고, 월별은 "2026년 8월 성적" 류
   롱테일이라 검색 수요가 사실상 없다.

→ 다시 볼 조건: 월 구간 집계 API 가 생기고(그래야 본문이 있다), 누적 `/record` 가 타겟 쿼리에서
노출을 잡기 시작한 뒤. **판단은 2026-10-13 이후**(4~8주)에 한다.

**파비콘은 SEO 판단과 분리해 먼저 처리했다**(2026-08-18) — 5절 표 참고. 검색 노출 효과를
기대한 게 아니라 매 페이지 935KB 전송이 그 자체로 낭비였다.

## 4. 남은 과제 — 이길 수 있는 쿼리 정하기

여기가 실제 과제이고, **콘텐츠 전략 결정이라 착수 전 방향 합의가 필요하다.**
(2026-08-18 결정·1차 반영은 3-2 절 참고 — 아래는 그 결정의 근거와 남은 항목이다.)

### 왜 `/record` 인가
종가랩의 유일한 구조적 차별화는 [`/record`](../../../jongalab/frontend/app/record/page.tsx)다 —
**추천 종목의 실제 성적을 검증 가능한 형태로 공개**하는 것. 네이버금융·인베스팅닷컴은
추천을 하지 않으므로 성적을 공개할 수 없고, 추천을 파는 유료 서비스는 성적을 공개할 이유가 없다.
경쟁이 얕고 검색 의도가 명확한 유일한 지점이다.

노려볼 쿼리 후보: `AI 주식 추천 수익률` · `주식 추천 사이트 승률` · `종가베팅 승률` ·
`종가베팅 수익률` · `AI 추천 종목 성적`
