## 스케줄러 이관과 중단 사고

### 2026-07-13 — PM2 cron → 통합 스케줄러 1단계
저위험 잡을 `jongalab-scheduler`(PM2 상시 앱)가 spawn 하도록 이관하고 실행 이력을 `job_run` 에 남긴다.
창 민감/자금 인접 잡(telegram_listener·gap_check·closing_bet·news_guard·night_futures·token-refresh)은
PM2 cron 유지. 2단계는 `job_run` 2~3일 무사고 후.

### 2026-07-15 — 타임아웃 kill 이 자식을 고아로 남김
`uv` 부모만 죽이면 python 자식이 살아남아 중복 실행·DB 중복키 충돌을 일으킨다.
→ 프로세스 그룹 단위 kill(`start_new_session` + `killpg`).

### 2026-07-15 — 배포 훅 재시작 끊김으로 이틀 무감지 중단
스케줄러가 죽어도 스스로 알리지 못한다(잡이 안 돌면 조용하다).
→ ① trading watchdog(평일 09:35)이 `job_run` 최신 기록이 2시간 이상 오래되면 경보
(`youtube_collector` 가 15분 주기라 살아있으면 항상 신선하다).
배포 훅도 재시작 후 online 검증·재시도를 하도록 보강.
이 중단으로 7/15·7/16 `after_hours_labels` 가 미실행 — 리스크·체결강도 6종은 7/17 일별 시계열 TR 로
소급 백필했지만 **ah_*(시간외 4종)·breadth 는 스냅샷 전용이라 이틀 영구 결측**이다.

### 2026-07-21 — PM2 데몬 재시작 후 resurrect 실패
scheduler 만 3시간여 방치됐다.
→ ② `scheduler_watchdog`(PM2 cron, 5분마다)이 `pm2 jlist` 로 상태를 확인해 online/launching 이
아니면 자동 재기동 + 경보. ①은 지연 감지(잡 이력 기반), ②는 즉시 자동복구(프로세스 기반)로 역할이 다르다.

## 워커 처리량·타임아웃

### 2026-07-15 — youtube_collector 재분석 루프
저장 안 하기로 **확정된** 영상(무관/기업없음/환각/티커없음)을 기록하지 않아 15분마다 같은 영상을
Ollama 로 재분석해 잡이 타임아웃됐다 → `content_skip` 기록.
일시적 실패(자막 미생성·LLM 오류)는 기록하지 않아 다음 주기 재시도.

### 2026-07-21 — 잡 타임아웃 방어 3중
① 소프트 데드라인 `RUN_BUDGET_SEC=300`(초과 시 새 채널 처리 중단, 남은 영상은 다음 주기)
② `OLLAMA_TIMEOUT=480s`(300+480<840 이라 SIGKILL 원천 불가)
③ 같은 영상이 연속 3회 LLM 타임아웃이면 확정 스킵.
**타임아웃만 카운트**한다 — 연결 실패(Ollama 다운)·파싱 실패를 세면 인프라 장애가 정상 영상을 영구
스킵시킨다.

### 2026-07-29 — telegram_listener 이벤트 루프 블로킹
채널 15→28 확장 시, 동기 LLM 호출이 분석(건당 평균 152초, CPU 추론) 동안 루프를 세워 뉴스 적재가
07~09시대 평균 145초·최대 22분 밀렸다 — `news_guard` 의 개장 전 악재 판정이 09:28 청산 이후로 밀릴 수
있었다. → `asyncio.to_thread` 로 분석을 스레드에 내보내고 세마포어로 동시 1건(Ollama CPU 직렬).
- 처리량 상한 **시간당 ~24건**. 느린 원인은 **출력 토큰**이다(실측): 입력 prefill 1,650~1,700토큰 = 5초인데
  출력 decode 가 5.7 tok/s 라 건당 152초의 95%가 출력. → `num_ctx` 축소·원문 절단으로는 거의 못 줄이고
  **출력 필드 축소 또는 더 작은 모델**만 유효하다.
- 반대로 `num_ctx`(기본 4096)를 줄이면 프롬프트가 한도를 넘을 때 **앞쪽 지시문부터 잘려** JSON 형식
  지시가 사라지고 파싱 실패가 된다(현재 여유 ~2,400토큰 ≈ 원문 5,000자까지 안전).
- 감시 목록은 **기동 시 1회** 읽으므로 채널 추가·삭제 후엔 재시작이 필요하다 — 2026-07-29 신규 16채널이
  재시작 전까지 수집 0이었다.

### 2026-08-06 — 전달(forward) 메시지 중복 제거
감시 중인 채널의 전달 메시지는 원본 경로로도 들어와 `news_mention` 언급 **건수**를 부풀린다.
→ `fwd_from` 원본 peer id 가 감시 대상이면 `content_skip(reason='forwarded')`.
**경로별로 분리**해야 한다(일반 핸들러는 `platform='telegram'` 집합만, 뉴스 핸들러는 `'news'` 집합만) —
교차로 거르면 일반 채널이 전달한 뉴스의 LLM 분석이 사라지거나 언급 1건이 사라진다.
원본이 숨겨진 익명 전달은 못 걸러 본문 dedup(6h)으로 넘어간다.

### 2026-07-29 — 텔레그램 알림 파싱 실패
콘텐츠 알림을 원문 인용 형태로 바꾸면서 `parse_mode=HTML` 로 전환했다. 원문의 임의 문자(`*`·`_`·`[`)가
Markdown 파싱을 깨 알림이 **조용히 누락**되던 문제도 함께 막혔다(예외를 삼키고 로그만 남기는 구조라
눈에 띄지 않던 실패).
봇 계정으로는 네이티브 전달(forwardMessage)이 불가능하다 — 수집은 Telethon 사용자 세션, 발송은 봇이고
봇은 멤버가 아닌 채널의 메시지를 전달할 수 없다.

## 달력·권리락

### 2026-07-17 — 제헌절 오실행
`exchange_calendars` XKRX 에 없는 신규 공휴일이라 워커가 휴장일에 돌았다.
→ `EXTRA_HOLIDAYS` 수동 오버라이드 + 전 워커 진입부 거래일 가드.
⚠️ **jongalab·trading 양쪽 복제본에 함께 추가해야 한다.**

### 2026-08-04 — 권리락 매수 스킵 (알테오젠 계기)
알테오젠 종가 346,500 → 익일 기준가 267,000(무상증자 1주당 0.3주 = -23%). 공짜 신주는 신주 상장일
(보통 3주 뒤)에나 들어오고 1주 매수면 단수주라 현금으로 와서 **그 자리에서 상계되지 않는다**.
검증된 엣지(종가→익일시가)와 성격이 다른 거래라 **회피**를 택했다.
⚠️ **평단 보정은 하지 않는다** — 평단은 하드손절선의 기준값이라 추정 비율이 틀리면 손절선이 조용히
움직이고, 가격만 보정하면 수량 보정이 3주 뒤라 반쪽이다.
권리락일 판정은 DART `fricDecsn` **신주배정기준일 직전 영업일**. 자율공시 건은 기준일을 못 얻어
`source='inferred'` 로 공시일 직후 2영업일을 과잉 등록한다(실측 간격이 +1·+2영업일로 갈린다).

### 2026-08-04 — 권리락이 라벨을 오염시킴 (대동기어)
수정주가 일봉은 권리락을 소급 조정하지만 분봉·NXT 시세·`krx_close_price` 는 실거래가 그대로라,
**미조정 가격으로 만드는 라벨만** 배정비율이 손실로 찍힌다: 8/3 19:50 분봉 9,594 → 8/4 09:03 분봉 7,510
= -21.7%, 실제로는 그날 +1.76% 상승이고 ±35% 가드도 통과했다.
공시일로는 판정 불가(공시→권리락 간격이 종목마다 다르다 — 알테오젠 8/4 공시→8/5 권리락 /
대동기어 7/31 공시→8/4 권리락)라 **수정 일봉 종가 ↔ 실거래 종가의 스케일 불일치**(허용 2%)로 감지한다.
2026-08-03 유니버스 48행 전건 일치 = 오탐 0.

### 2026-08-05 — 권리락일 갭 측정 조정 (sql/50)
갭 확정일이 권리락일이면 기준가를 `전일가 / (1 + 배정비율)`로 되돌려 측정한다.
실측 알테오젠: 346,500→286,000 = -17.46% 로 저장·알림됐지만 조정 기준가 266,538 대비 **+7.30% 상승**이었다.
`source='inferred'`(ratio NULL) 행은 조정하지 않고 경고만 — 권리락일 자체가 추정이라 잘못 조정하면
정상 종목의 갭을 망친다.

## 설정·보안

### 2026-08-05 — .env 변경이 잡에 반영되지 않는 함정
`load_dotenv` 는 기존 env 를 덮어쓰지 않고(`override=False`), `jongalab-scheduler` 는 자식 잡을
`env={**os.environ}` 로 spawn 하므로 **재시작 전에는 스케줄러가 물고 있던 옛 값이 상속된다**
(`OPENAI_MODEL` 교체 때 실제로 걸렸다).
PM2 cron 잡은 pm2 데몬 env 에 해당 키가 없어 매 spawn 시 `.env` 를 새로 읽으므로 재시작이 필요 없다.

## 메모리에서 이관 (2026-08-06)
아래는 세션 메모리에 쌓여 있던 판정 기록을 원문 그대로 옮긴 것이다(`[[링크]]` 는 다른 이관 항목 제목을 가리킨다).

### scheduler-migration-phase1
> PM2 cron → 통합 스케줄러(jongalab-scheduler) 1단계 이관 완료(2026-07-13), 2단계 조건·롤백 방법

PM2 워커 통합 계획 (n8n 검토 → 자체 스케줄러로 결정, 2026-07-13):

- **1단계 완료(2026-07-13)**: `jongalab/workers/scheduler.py`(APScheduler, PM2 상시 앱 `jongalab-scheduler`)가
  저위험 잡 7개(youtube_collector·cleanup_content·news_ticker_seed·outcome_backfill·after_hours_labels·
  rule_evaluator·weight_tuner)를 서브프로세스 spawn. 실행 이력 `job_run` 테이블 + `/admin/jobs`
  워커 현황 페이지 + 실패 시 관리자 텔레그램 경보. 구 PM2 앱 7개는 delete 됨.
- **2단계(대기)**: job_run 이 2~3일 무사고면 gap_check ×4·closing_bet·token-refresh·kis_night_futures 이관.
  트리거: "스케줄러 2단계 이관하자".
- **3단계(계획 없음)**: trading 자금 경로(buy/settle/monitor/fills_sync/reconcile/watchdog)는
  의도적으로 PM2 잔류 — watchdog 독립 안전망 유지가 이유. 장기 무사고 후에만 재논의.

**Why:** n8n 이관은 로직이 Python 에 남아 이득이 없고(껍데기만 이동), 관리부담·시각화는
스케줄러 통합 + job_run 대시보드가 해결. 자금 경로는 리스크 대비 편익이 없어 제외.

**How to apply:** 잡 추가/스케줄 변경은 scheduler.py `JOBS` 만 수정(재시작은 배포 훅이 수행).
day_of_week 는 반드시 이름("mon-fri")으로(APScheduler 숫자 요일은 0=월이라 표준 cron 과 다름).
롤백: 루트 `ecosystem.config.js.bak`(이관 전 전체 정의) 참고해 해당 앱 블록 복원 →
`pm2 start ecosystem.config.js --only <name>` + scheduler JOBS 에서 제거.
관련: `validation-schedule`

### ollama-port-exposure-0729
> 2026-07-29 Ollama 11434·MariaDB 3307 이 인터넷에 열려 외부 추론이 성공하던 것을 발견해 127.0.0.1 바인딩으로 차단 — 남은 확인 항목(정체불명 모델·매시 embeddings 클라이언트)

2026-07-29 텔레그램 채널 확장 성능 조사 중 발견: `docker-compose.yml` 의 ollama(11434)·mariadb(3307)
포트가 **전체 인터페이스(0.0.0.0)** 에 published 되어 인터넷에서 직접 접근 가능했다. Ollama 는 인증이
없으므로 외부 IP 들이 실제로 추론을 성공시키고 있었다 — `POST /api/generate` 200 (33s·7s·6.8s·4.5s),
`/api/chat` 200, `118.194.252.175` 가 **매시 :14분** `/v1/embeddings` 200(59회), `103.216.158.236` 이
`/api/tags`·`/api/ps` 를 1,470회 폴링. 조치: 양쪽 ports 를 `127.0.0.1:...` 바인딩으로 바꾸고 컨테이너
재생성(ollama 08:41, mariadb 는 자금 경로 창 09:30 이후로 미뤄 실행). 로컬 PM2 앱은 무영향.

**Why:** 이 박스는 GPU 가 없어 **CPU 추론**이고(`/api/ps` size_vram=0) LLM 처리량이 파이프라인의
하드 병목이다(시간당 ~24건). 외부 요청이 같은 CPU 를 먹으면 그대로 분석 지연이 된다 — 실제로 prefill 이
프리픽스 캐시 히트 시 2~3초인데 미스/경합 시 19~80초까지 튀었다. 보안 문제이면서 성능 문제였다.

**How to apply:** 남은 확인 2건 — ① `/api/tags` 에 프로젝트가 쓰지 않는 로컬 모델이 있다:
`qwen3.6:27b`(17.4GB, 7/17), `hermes_pwn:latest`(7/6) + `:cloud` 별칭 22개(최근 7/7). 사용자 본인이
실험용으로 pull 한 것인지, 열린 포트로 외부가 `/api/pull` 한 것인지 확인 후 정리 판단(디스크 17GB+).
② 매시 :14분 embeddings 클라이언트가 사용자님의 원격 서버였다면 이제 끊긴다 — 그 쪽 로그 확인 필요.
포트를 다시 열 일이 생기면 바인딩 해제가 아니라 방화벽 화이트리스트(`ufw allow from <IP>`)로 한다.
관련: `validation-schedule` 16번(텔레그램 채널 소화력).
